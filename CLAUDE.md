# Life Hub

Personal life hub for one user (Mike). iOS + macOS, native SwiftUI. A companion
character (RUNNER, Rive) mirrors the current mode and energy.
Docs (Obsidian markdown, mirrored from Mike's vault): `docs/05 Engineering/技术架构.md` (architecture),
`docs/05 Engineering/范围文档.md` (scope), `docs/03 Product/Hub PRD.md` (features).

## Stack
- Swift 6, SwiftUI, deployment targets iOS 26 / macOS 26. No cross-platform frameworks.
- SwiftData + CloudKit private database for sync. NSUbiquitousKeyValueStore for the current mode.
- Rive via rive-ios (SPM). Only `Packages/CompanionKit` may import RiveRuntime.
- No custom backend.

## Build
- The Xcode project is generated by XcodeGen from `project.yml` and is not committed.
  `brew install xcodegen && xcodegen generate && open LifeHub.xcodeproj` (or `make open`).
- Package tests: `swift test --package-path Packages/HubCore`.
- Before pushing: `make check` (swift-format lint, tests, HubCore coverage gate). `make format` fixes formatting.
- CI (`.github/workflows/ci.yml`, details in `docs/05 Engineering/CI-CD.md`) blocks a PR on: PR title /
  branch name, formatting, lint, tests, HubCore line coverage < 80%, warnings in packages or app builds.
  Never lower the coverage gate or disable a rule to get green; fix the code or add the test.
- `release.yml`: merge to `main` uploads STG to TestFlight; tag `vX.Y.Z` uploads PROD. Both run CI first.

## Process (details: `docs/05 Engineering/开发流程.md`)
- Trunk-based. Branch from `main` as `feature/<issue>-<name>`, `fix/…`, `chore/…`, `docs/…`;
  `hotfix/<version>` from a release tag only when PROD needs a fix and `main` has unreleased work.
- Every change goes through a PR: one thing per PR, Conventional Commits title, squash merge, CI green,
  PR template filled in (Before / After / How, verification level).
- Environments = Xcode configurations: Debug = DEV (`.dev`), Staging = STG (`.stg`, TestFlight internal),
  Release = PROD (`com.guanshiyang.lifehub`). Separate data and, later, separate CloudKit containers.
- SemVer in `MARKETING_VERSION` (0.x until the MVP; M0 = 0.1.0), build number +1 per upload,
  PROD releases tagged `vX.Y.Z`, `CHANGELOG.md` updated in each feature PR under [Unreleased].
- Never commit signing team IDs, certificates or keys.

## Layout
- `Apps/iOS`, `Apps/macOS`: UI and platform glue only.
- `Packages/HubCore`: models, ModeEngine, StateEngine, sync, App Intents, Assistant protocol.
- `Packages/CompanionKit`: CompanionView / CompanionController wrapping Rive.
- `Packages/SideHustleKit`: macOS-only tools and UI (content calendar, reference library, data import,
  bookings). Side-hustle models (ContentItem, Reference, Booking) live in HubCore so iOS can show them.
Logic goes in packages, with unit tests. If iOS and macOS need the same logic, it belongs in HubCore.

## Core model rules
- Mode (what Mike is doing: work, chill, boxing, money) and State (energy 0-100, load, confidence)
  are separate types. Never derive one by overloading the other.
- Manual mode changes always win. Automatic sources (Focus filter, calendar, geofence, schedule)
  may suggest, or switch only under rules Mike enabled; no auto-switch for 2h after a manual change.
- Every ModeChange is stored with its source.
- Exception: entering the boxing gym geofence (CLMonitor, ~100 m) switches straight to boxing with no
  prompt, even within the 2h window. Leaving after 30+ min restores the previous mode unless Mike
  changed mode manually at the gym. Gym location lives in app settings, never in code or the repo.
- Chill sub-activities (groceries, shows, gym) are an optional tag on ModeChange, not separate modes.
- StateEngine is rule-based and explainable. Each output carries the reasons that produced it.
- Interventions: L0 companion expression only, L1 one line when the app is opened,
  L2 push notification max 1/day with a 3h cooldown. Low energy + low load is rest: do nothing.

## Companion
- Data Binding only (no legacy state machine Inputs). View Model `Runner` in
  `Packages/CompanionKit/Sources/CompanionKit/Resources/runner.riv`:
  `mode` enum (work, chill, box, money), `energy` number 0-100, `tap` trigger (fired inside Rive
  by a Listener), `cheer` trigger (fired by the app). Keep names in sync with the .riv file.
- Swift `Mode.boxing` maps to Rive `"box"`; that mapping lives only in CompanionKit.
- Widgets, Lock Screen and Live Activities use static per-mode images, not Rive.

## Principles (carried over from Mike's work hub)
- Rules before models. Tiers: T0 rules, T1 on-device Foundation Models, T2 Claude Sonnet (macOS),
  T3 Claude Opus only when Mike explicitly asks. Every feature declares its tier; log usage and cost.
- Models only return text. Anything a model proposes is shown as a suggestion card and written only
  after Mike accepts it.
- One source of truth per data type, one writer per field. Structured data: SwiftData + CloudKit.
  Long-form notes: Mike's Obsidian vault (macOS writes only under its `Hub/` folder, previewed first).
  Daily exports to the vault are one-way, read-only copies.
- Evidence levels on mode changes: manual > geofence/Focus > calendar/schedule > inferred. Show inferred ones differently.
- Energy is derived from an append-only EnergyEvent log, not a mutable number.
- Surface errors (sync, permissions) in the UI; never swallow them.
- Idempotent event handling: every location event, import row and notification has an id and is applied once.
- No data from Mike's work hub or company systems enters this app.

## Lessons from Lilo and Daily Widget
- Before each step, look up the scenario table in `docs/00 Lessons/经验索引.md` and read the matching
  entries' gotchas (e.g. sync → DW-02, DW-06, DW-01; data model → DW-02, DW-05; widgets → DW-04;
  first TestFlight → DW-05, L-05, L-RELEASE). Full source notes live on Mike's Mac; ask for one if
  the gotchas aren't enough.
- Every core feature must give value on a day Mike does nothing. Automatic mode switching and widgets
  come before anything that needs manual logging.
- Record state and summaries (mode timeline, energy events), not task lists.
- Prove one loop before adding screens. No placeholder buttons: anything shown in the UI works.
- The app computes; widgets read a `WidgetSnapshot` written to the App Group container.
- Data contract first: every record has schemaVersion, id, createdAt, updatedAt, updatedBy (device id),
  deletedAt (soft delete). Decoding tolerates missing fields with defaults. Unit-test the Codable types.
- An older build must never delete newer data on save (DW-02): `ModeLog` keeps unreadable records and
  writes them back. Unknown fields on readable records are still dropped; fix that before two
  builds write the same store.
- Evidence levels: "compiles", "verified locally on two real devices", "shipped via TestFlight" are
  different claims. Sync is only verified on a real iPhone + Mac, never on simulators alone.
- Bundle id prefix: com.guanshiyang.lifehub; App Group group.com.guanshiyang.lifehub.

## Privacy (hard rules)
- Raw HealthKit data is read in place, never copied, never synced, never sent off device.
- Only the derived energy band syncs to the Mac.
- Location and health data never go to any network API, including Claude.
- Secrets (Claude API key) live in Keychain only. Never commit keys.
- On-device Foundation Models for companion lines; Claude API only for side-hustle analysis on macOS.

## Working style
- Small PRs, one feature each. Build both iOS and macOS targets before calling something done.
- Run unit tests for any package you touched.
- UI follows style E (toy / neo-brutal: thick black outline, flat bright colors, hard shadow);
  use the `Toy` tokens in CompanionKit, no ad-hoc colors.
- Ask before adding a dependency.
