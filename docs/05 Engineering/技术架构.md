# Life Hub 技术架构

> 一个产品、两个端。iOS 负责情绪价值和切换状态，Mac 是总控台 + 副业工具。两端共用一套 Swift 核心。
> 相关：[[Life Hub 方向]] · [[Hub PRD]] · 参考了工作中的 Attention Hub（第 13 节） · [[副业平台可行性]] · [[CLAUDE.md 草稿]] · companion 设定稿 [RUNNER v5](https://claude.ai/artifact/Vny8JZBtb37WtkUkKiwUPY)

## 1. 关键决定（一览）

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| 客户端技术 | **原生 SwiftUI 多平台**，一个 Xcode 工程，iOS + macOS 两个 target | 要用 HealthKit、Focus、小组件、灵动岛、菜单栏，跨平台框架都要绕路 |
| 最低系统 | **iOS 26 / macOS 26** | 只给 Mike 自己用，不需要兼容旧机；能直接用 Liquid Glass、端上 Foundation Models、SpeechAnalyzer |
| 共享核心 | 一个本地 Swift Package `HubCore` | mode、状态引擎、companion、数据模型只写一遍 |
| 数据和同步 | **SwiftData + CloudKit 私有库** | 不用自己架服务器，免费，数据在 Mike 自己的 iCloud |
| companion | **Rive**（rive-ios，MIT）Data Binding，一份 `runner.riv` 两端共用 | 设定稿和 Rive 搭建步骤已按 View Model 设计 |
| 状态引擎 | 先用**规则**，不上模型 | 数据少、可解释；规则跑稳了再考虑学习 |
| AI | iOS 端用系统自带的**端上模型**（Foundation Models）写 companion 台词；Mac 端用 **Claude API** 做副业分析 | 健康数据不出手机；重分析放 Mac |
| 副业工具 | **不爬虫、不自动发帖**，走官方创作者平台 + 手动收集 + 导入 | 两个平台都禁止，抖音发布接口个人申请不了，见 [[副业平台可行性]] |
| 自建后端 | **暂时不要** | 一个人用，iCloud 够了；以后要接单页面再说 |

## 4. Mode 与状态：两个东西，分开建模

这是整个架构最重要的一点：**mode 是 Mike 在做什么，state 是 Mike 状态怎么样**。两者正交。

- **Mode**（离散，Mike 说了算）：`work` · `chill` · `boxing` · `money`，以后可加。
- **State**（连续，系统估计）：沿用之前的 Energy × Load 模型，加一个置信度。

### 4.1 ModeEngine

```swift
enum Mode: String, Codable, CaseIterable { case work, chill, boxing, money }

struct ModeChange {           // 存一条历史，供以后学习
    let mode: Mode
    let at: Date
    let source: Source        // .manual / .focus / .schedule / .location / .suggestion
}
```

- **手动永远优先**。自动来源只能“建议”或在 Mike 设过的规则下切换，手动切换后 2 小时内不自动改（地点触发例外，见下）。
- 自动来源（都是苹果官方能力，没有灰色接口）：
  - **专注模式（Focus Filter）**：Mike 打开 iPhone 的“工作”专注 → Hub 进 work mode。这是最省事的入口。
  - **日历**：日程标题里有“拳击”→ 当天进 boxing。
  - **地点（Mike 2026-10-02 确认：检测到就直接切，不弹确认）**：进入拳馆地理围栏 → 直接切 boxing，并触发一次 `cheer` 打气；离开围栏且已待满 30 分钟 → 切回进拳馆前的 mode（练完一般是 chill）。
    - 实现：iOS 17+ 的 `CLMonitor` + `CircularGeographicCondition`，半径约 100 米。系统在后台唤醒 App，耗电很低；需要“始终允许”定位权限。
    - 拳馆坐标存在 App 设置里（Mike 自己填地址，App 本地转坐标），**不写进代码和仓库**，也不同步到 Mac 以外的任何地方。
    - 地点触发是“明确信号”，不受下面“手动后 2 小时不自动切”的限制；但 Mike 在拳馆里手动改了 mode，离开时就不再自动切回。
  - **时间表**：工作日 19:00 后建议 chill。
- 切换入口：App 内、iOS 控制中心按钮、锁屏小组件、Siri/快捷指令（App Intents）、Mac 菜单栏。

### 4.2 StateEngine（规则版）

输入（已在 [[MVP 计划草稿]] 核实过可用）：HealthKit 睡眠和 HRV、日历密度、mode 历史、Mike 手动点的“我很累/我很好”。**不用 Screen Time**（数据出不了沙盒）。

输出：`energy: 0–100`、`load: low/mid/high`、`confidence`。
介入分级沿用：L0 只变 companion 表情 → L1 打开 App 时说一句 → L2 主动通知（每天最多 1 条，3 小时冷却）。低 energy + 低 load = 正常休息，不打扰。

计算只在 iPhone 上做；同步到 Mac 的只有算出来的 `energy` 档位，不同步原始健康数据（见第 7 节）。

## 5. Companion（Rive）接入

按 [[Rive 搭建步骤]]：Rive 已把状态机 Inputs 标为旧系统，所以 companion **只用 Data Binding**。`runner.riv` 里有 View Model `Runner`：

| 属性 | 类型 | 谁写 |
| --- | --- | --- |
| `mode` | Enum `Mode`：work / chill / box / money | App，来自 ModeEngine |
| `energy` | Number 0–100（<30 显示没电） | App，来自 StateEngine |
| `tap` | Trigger | Rive 内部的 Listener 自己触发，App 不用管 |
| `cheer` | Trigger | App：完成一件事、发布成功、接到单、拳击练完 |

- Swift 里的 `Mode.boxing` 写入 Rive 时映射成 `"box"`，映射只写在 CompanionKit 一处。
- `CompanionKit` 对外只暴露：

```swift
struct CompanionView: View { let mode: Mode; let energy: Double }
final class CompanionController { func cheer() }
```

  App 代码不碰 Rive API。以后换 Lottie 或自绘，只改这一个包。
- 一份 `runner.riv`，iOS 主页、Mac 总控台、Mac 菜单栏都用它。小组件和锁屏**跑不了 Rive 动画**，用设定稿导出的静态图（`runner-v5-*.svg`，按 mode 切换）。
- 切 mode 的过渡第一版用 Rive 里的 `pop` 动画盖过去，耳机落下、拉面罩这类专属过渡等 M1 用顺了再加。
- **免费版导出的 .riv 带 Rive 启动画面**，自己用先接受；介意的话 Cadet 档 $9/月可去掉。
- rive-ios 有两套 API：旧的 `RiveViewModel` + `enableAutoBind`，和新的异步 API（`File` / `Worker`）。**选新 API**，因为它能把渲染放到后台线程，Mac 菜单栏常驻更省电；如果 spike 里新 API 在 macOS 上有问题，退回旧 API，只影响 CompanionKit 内部。
- rive-ios 支持 iOS 14+ / macOS 13.1+，SPM 安装。M0 spike 要验证两件事：Mac 菜单栏里常驻的 CPU 占用，以及启动画面在菜单栏这种小尺寸下是否碍眼。

## 6. iOS ↔ Mac 同步

- **SwiftData + CloudKit 私有库**：模型定义在 HubCore，两端同一个 container。冲突策略：最后写入为准，mode 切换本来就是“最新的算数”。
- “当前 mode” 需要秒级生效：除了 SwiftData，再写一份到 `NSUbiquitousKeyValueStore`，两端监听变更立即刷新 companion。
- 离线照常用，联网后自动同步。
- 需要 **Apple Developer Program（每年 99 美元）**：CloudKit 和推送必须付费账号；免费账号装的 App 7 天就过期。

## 7. 本地数据与隐私

| 数据 | 存哪 | 同步吗 |
| --- | --- | --- |
| HealthKit 原始数据 | 只在 HealthKit 里读，不复制 | 不同步 |
| 算出的 energy / load | iPhone SwiftData | 只同步档位 |
| mode 历史、日程、待办、副业内容 | SwiftData | 同步 |
| 照片、视频素材 | Mac 本地文件夹（或 iCloud Drive），库里只存路径 | 文件夹自己同步 |
| Claude API key、平台账号 | Keychain | 不同步 |

原则：没有自己的服务器；发给 Claude API 的只有副业内容（公开笔记的文字、Mike 自己的数据导出），**健康数据和位置永不出设备**。

## 8. Mac 副业模块（SideHustleKit）

详细的平台核查见 [[副业平台可行性]]。结论：**Hub 做“内容工作台 + 数据看板 + 接单管理”，发布和数据走官方创作者平台**，不碰爬虫和自动化登录。

| 需求 | 方案 | 风险 |
| --- | --- | --- |
| 参考账号研究 | Mike 在手机/电脑上看到好笔记 → 分享链接或截图到 Hub（iOS 分享扩展）→ Mac 用 Claude 做拆解：选题、封面构图、标题句式、发布时间、互动数 | 低：手动收集、自己看 |
| 定时发布 | Hub 管内容日历和素材包（成片、封面、标题、话题、文案）→ 到点提醒 → 打开官方创作者平台网页，文案已在剪贴板 → 在官方平台里设“定时发布” | 低：发布动作在官方平台 |
| 流量分析 | 每周从创作者中心导出数据（或手动录几项关键数）→ 导入 Hub → 看板：涨粉、完播/阅读、收藏率、哪类内容好 | 低 |
| 接单（摄影） | 询单 → 报价 → 档期 → 拍摄 → 交片 的小 CRM，和日历打通 | 无 |
| 短片生成（副业二） | 剧本模板 + 5–10 张照片 → 调 AI 视频模型生成；**等副业二细节讨论完再设计**，先留模块位置 | 看所用模型的条款 |

明确不做：无头浏览器登录、逆向签名（xsec_token 之类）、用主账号跑 RPA 自动发帖、批量抓别人主页。

## 12. 和 PM 文档的对齐（[[Hub PRD]]）

- **数据模型**按 PRD v2 第 10 节落在 HubCore：`Mode`、`ModeChange`、`EnergySample`（来源：睡眠 / 自评）、可选的 `DailyCheckin`、`GoodMoment`（好回忆）。PRD 的 ModeSwitch 来源“自动 / 手动纠正 / 建议”在代码里更细：自动拆成 `location` / `focus` / `calendar` / `schedule`，手动纠正就是自动切之后的 `manual`，另有 `suggestion` 和 `inferred`，这样能按证据等级显示；副业的 `ContentItem`、`Reference`、`Booking` 模型也放 HubCore（同步到 iOS，用来显示今天的副业待办和发布提醒），SideHustleKit 只放 Mac 端的工具和界面。
- **小组件 / 菜单栏读当前 mode**：App Group 共享的 SwiftData 存储 + `WidgetCenter.reloadTimelines`；交互式小组件用 App Intent 直接切 mode。
- **过渡动画**（PRD 第 4 节）：放在 Rive 里做，不在 SwiftUI 里拼。第一版用 `pop`，专属过渡以后加，和 [[Rive 搭建步骤]] 一致。
- **Q5 参考采集**：工程意见是 Mike 自己在浏览器里点“收藏到 Hub”，插件只保存当前这一页的链接、标题、截图，可以做（P1）。**定时去别人主页批量抓不做**，那就是爬虫，违反小红书协议 4.1。
- **Q6 自动发布**：同意 PRD 的建议，只做“到点提醒 + 素材备好 + 手动发”。模拟浏览器发布不做。
- **Mike 的回答（2026-10-02）**：Q1 就 4 个 mode；Q2 买菜/看剧/健身做成 Chill 里的标签（`ModeChange` 加可选 `tag` 字段）；Q3 地点检测到直接切（见 4.1）；其余同意 PRD 建议。
- **Q8 数据放哪**：iCloud 够。以后真要给合作者看，再单独加一个导出或共享页面，不为此提前建后端。

## 13. 从工作 Hub（Attention Hub）借鉴的

Mike 2026-10-02 发来了工作中的 hub（localhost Python + 原生 JS，Obsidian vault 当数据源）。它的 10 条原则大多能搬过来，但形态不同：这里是原生 App、要上手机、没有常驻的本地服务器。

### 直接搬过来

| 工作 Hub 原则 | 在 Life Hub 里 |
| --- | --- |
| 1 能不用模型就不用（T0 规则优先） | 状态引擎、mode 自动切、通知去重、数据导入全是规则。**模型分级**照搬：T0 规则 → T1 端上 Foundation Models（companion 台词、短文本分类）→ T2 Claude Sonnet（Mac 副业拆解、文案）→ T3 Claude Opus 只在 Mike 点 “Ask Claude” 时用。每个功能声明自己的 tier，Mac 顶栏显示当天调用次数和费用 |
| 2 模型只出文字，代码负责写 | Claude 拆解参考笔记、写文案、排内容日历，结果都是**建议卡片**，Mike 点“收下”才写进数据库 |
| 3 PROD 只由人执行 | 对应“发布只由 Mike 按”。Hub 准备素材包和文案，发布在官方平台里由他本人点 |
| 4 数据源只有一个 / 每份数据只有一个写入方 | 见下面“数据源” |
| 6 证据分等级 | mode 切换按来源分级：手动 > 地点/Focus > 日历/时间表 > 推断。时间轴上推断出来的切换用虚线显示，和工作 Hub 的 IMPLIED 一样 |
| 7 读真实的数据源 | HealthKit、日历都原地读，不复制 |
| 8 错误要显示出来 | 顶部一个 SYNC 状态点：iCloud 同步失败、定位权限被关、HealthKit 没授权都变红，悬停看原因 |
| 9 幂等 | 地点事件、导入的数据行、通知都带唯一 id，只处理一次；L2 通知用“同一个 key 一天只提醒一次”的去重 |

### Attention Bank 面板和 Rituals

- 工作 Hub 的 Attention Bank（能量罐 0–100、低电量/还行/满格、专注/休息/被打断按钮、按天的事件流水 `bank/DATE.jsonl`）和这里的 energy 是同一个概念。Life Hub 沿用它的**事件模型**：`EnergyEvent { kind: focus / rest / interrupt / checkin / boxing / switch, at, delta, source }`，energy 由事件流算出来，而不是存一个数字反复改。
- **Rituals** 搬过来：Morning（早上一句今天的 mode 安排）、Wrap（就是 PRD 的晚间 10 秒记录）、Weekly（周日的副业复盘）。全部 T0，不调模型。

### 数据源：不照搬 “vault 是唯一数据源”

工作 Hub 只在 Mac 上跑，读 Desktop 上的 vault 很自然。Life Hub 的 iPhone 读不到 Mac 桌面上的文件夹，而 mode、energy 这类数据要秒级同步，所以：

- **结构化数据**（mode、energy 事件、晚间记录、内容日历、接单）：唯一数据源是 SwiftData + CloudKit。
- **长文**（参考笔记拆解、拍摄计划、短片剧本 template、周复盘）：唯一数据源是 Obsidian vault 里的 markdown。Mac 端按 Rules 只往 vault 里一个子目录（例如 `Hub/`）写，写之前给预览。
- Mac 端每天把当天的 mode 时间轴和晚间记录**单向导出**成一篇 Obsidian 日记，方便 Mike 在 vault 里回看。导出的文件是只读副本，改它不会回写。

### 以后再用

- **原则 5/10（做事的 agent 自己报告，Hub 管看板）**：短片生成（M3）这种需要长上下文的活，交给 Mac 上的 Claude Code 会话去做，做完在 vault 笔记的 `## Progress` 里追加一行，Life Hub 用同样的正则解析、勾选进度。到时直接复用工作 Hub 的行格式。

### 不接的

- **不把工作 Hub 的数据接进 Life Hub。** 工作 Hub 连着公司的 Teams、邮件、Jira，这些不应该进个人 iCloud。工作日的 mode 由 Focus、地点和时间表判断就够了。如果以后真想让“今天会很多”影响 energy，只从 iPhone 日历读工作日程的数量，不碰内容。

## 14. 从 Lilo 和 Daily Widget 学到的（2026-10-02）

两个前作都是因为“要 Mike 打开 App、手动记录才有用”而停用的。这条直接改变架构的优先级：

| 教训 | 对 Life Hub 的影响 |
| --- | --- |
| 1 不打开 App 也要有价值 | 每个 P0 功能都要回答“今天 Mike 什么都不做，它还有用吗”。mode 自动切（地点、Focus、时间表）和小组件从 M2 **提前到 M1 的一部分**：至少拳馆围栏和工作日时间表在 M1 就要有，否则 M1 只是又一个需要手动点的 App |
| 2 “明天还想打开吗”是验收信号 | 每个切片自己用满一周再扩。里程碑完成标准里加一条：Mike 一周后仍主动打开 |
| 3 记状态和摘要，不记任务清单 | 核心数据是 mode 时间轴和 EnergyEvent，不是待办。副业的内容日历是例外（它本身就是计划），但不做通用 todo |
| 4 先跑通一个动作闭环，再加页面；先写停止条件 | M0 只有一个闭环：mode 变 → companion 变 → 小组件变 → Mac 跟着变。见下面的停止/缩减条件 |
| 5 不做社交；界面上出现的功能必须真的能用 | 没接好的功能不放占位按钮 |
| 6 入口是小组件和通知；App 计算，小组件读快照 | 照 Daily Widget 的做法：App 写一份 `WidgetSnapshot`（当前 mode、energy 档位、下一件事、更新时间）到 App Group，小组件只读它，不直接查数据库 |
| 7 Mac 小组件要原生 SwiftUI；不自建后端和账号 | 和现有选择一致（原生多平台 + iCloud） |
| 8 先定数据契约，再写第二个端；两台真机测同步；源码、本地验证、上架版本是三个等级的证据 | 见下面“数据契约”。M0 的完成标准必须在 iPhone + Mac 两台真机上验证，模拟器不算 |

### 数据契约（写第二个端之前定死）

沿用 Daily Widget 的字段习惯，每条记录都有：`schemaVersion`、`id`(UUID)、`createdAt`、`updatedAt`、`updatedBy`(设备 id)、`deletedAt`(软删除)。解码时缺字段给默认值，旧版本数据不会让新版崩。M0 先定 `ModeChange`、`EnergyEvent`、`DailyCheckin`、`WidgetSnapshot` 四个，写成 HubCore 里的 Codable 类型加单元测试。

### 停止 / 缩减条件（开工前定）

- M1 用了两周，Mike 每天主动切 mode 少于 1 次，且自动切也没让他觉得有用 → 停下来重新讨论，不继续做 M2。
- 任何一个功能用一周后 Mike 没再碰 → 从界面上拿掉。
- Rive 在 Mac 菜单栏常驻 CPU 占用明显（spike 里测）→ 菜单栏改用静态图，只在打开面板时播动画。

### 从 Daily Widget 仓库确认的事实

- 它是原生 SwiftUI + WidgetKit，用 App Group（`group.com.guanshiyang.dailywidget`）共享快照，bundle id 前缀 `com.guanshiyang`。Life Hub 用同样的前缀：`com.guanshiyang.lifehub`。
- 它走 TestFlight 分发，Lilo 也是。TestFlight 需要付费开发者账号，所以**推断** Mike 已经有 Apple Developer Program（未向他确认）。
- 它的同步是 iCloud Drive 文件夹里一条记录一个 JSON 文件。Life Hub 改用 CloudKit，因为 mode 要秒级同步，文件夹同步太慢。

## 15. 已经做成的结构（随改动补记）

这一节记已经合进 `main` 的结构决定，前面几节是最初的计划。每个改动的 PR 同一回合补一条。

### App Group 和手表（2026-10-07）

- App Group 按环境分开：`group.com.guanshiyang.lifehub.dev` / `.stg` / 正式版不带后缀，写在 `project.yml` 的 `APP_GROUP_ID`，`Apps/iOS/AppGroup.swift` 照抄同一组 id。
- 用到 App Group 的 target：App、小组件、通知扩展、Screen Time 扩展、手表 App、手表小组件。每个 App ID 都要在开发者后台勾上同一个 group，少一个就装不上。
- 手表 App（Issue #160）：`$(APP_BUNDLE_ID).watchkitapp`，嵌在 iOS App 里，带自己的小组件。手表不计算，只显示 iPhone 发来的 `WatchPayload`。
- 第三方 App 做不了表盘，只能做复杂功能（accessoryCircular / Corner / Rectangular）。

### 每个角色各自的进度（2026-10-07，#201、#203）

- `CanEntry.persona`：每条罐子记录属于挣到时选中的角色。旧记录没有这个字段时，按它的商品属于谁来定，都没有就是 HAKU。
- `CanLedger.only(_:)` 取一个角色的账。生活记录用整本账（练拳周、网球日、今天的胜利、本周变化、回来的时候的起点）；游戏部分用一个角色的账（首页罐子、房间痕迹、隐藏属性、商店、衣柜、回来的时候、小组件）。
- 赢一次只付一次：赚到的 id 不带角色（`win:<win>:<source>`），换角色不会重复给。纪念品授予前先查 id，已有就跳过。
- 换角色要先确认（设置页弹窗），衣柜也按角色分开存。

### 运动分组（2026-10-07，Issue #205，PR #206）

- `WorkoutSummary.Kind` 分 13 组：走路、跑步、骑行、游泳、力量、拳击（含踢拳）、其他格斗、球拍、球类、瑜伽拉伸、舞蹈、户外、其他。
- HKWorkoutActivityType 到分组的对照只写在 `Apps/iOS/HealthMotion.swift` 的 `kind(_:)`。不认识的名字解码成“其他”。
- 罐子不变：只有拳击、5 km 跑步、力量（健身房）给罐。
- 苹果自带的体能训练 App 开始运动时，第三方 App 没有实时信号；HealthKit 在运动存好后才通知。所以只做“练完后按组演”，不做自己的 HKWorkoutSession。
- 运动存好后 HealthKit 在后台叫醒 App（`Apps/iOS/WorkoutObserver.swift`，HKObserverQuery + 后台通知，权限是 HealthKit 的 Background Delivery）。App 读一次最近运动，把该庆祝的那次作为事件发给手表，不标记“已庆祝”，所以手机下次打开还会演一次。睡前不发。还没答应健康权限时不读，免得和别的权限弹窗叠在一起。

### 手表播放首页的场景（2026-10-07，Issue #210，PR #211）

- 首页的场景规则（活动、时刻、走路、泡澡、vibe coding 的罐子）在 HubCore 的 `HomeSceneInputs`，首页和手表共用一份。
- iPhone 每次发给手表时，算好接下来 3 小时的场景（每 5 分钟看一次，只留变化的点），放在 `WatchPayload.scenes`。手表按当前分钟取，自己不计算。
- 场景不算表盘变化，不占复杂功能的每日传输次数。
- 手表只收比手上新的状态（`WatchPayload.replaces`，PR #209），两条通道先后乱了也不会被旧的盖掉。

### 通勤（2026-10-07，Issue #210，PR #212 和通勤接线 PR）

- 通勤只算家和公司之间：工作日离开家是去上班；不在上班模式时离开公司是回家（中午出去不算）。地点开始和结束，钟点不管。
- 到任何地方就结束；超过 2 小时没到也不算了；刚到就离开（路过）不算。
- 阶段：走路、在车上、到了。“到了”从到达起演 3 分钟，只演一次。规则在 HubCore `CommuteEngine`。
- 走路 / 在车上来自 iPhone 的运动协处理器（`Apps/iOS/CommuteMotion.swift`），要“运动与健身”权限。不持续监听：只在离开、到达家或公司的围栏事件和打开 App 时查一次离开以来的记录。所以 App 在后台时，上车要等下次打开或到站才变；判断不出就当走路。
- 运动数据只在 iPhone 本机用，不存、不上传。手表只收 `HomeScene.commute`（阶段 + 开始时间），跟着场景时间线走。
- 画面由 UI 线程做：`CompanionView` / `KuroView` 收 `commute`，首页和手表传 `scene.commute`。

### 下班按地点对账（2026-10-07，Mike：“状态切换优先看地点”）

- 起因：10-07 17:33 系统提前报了一次“离开公司”，当时被挡住没切（2 小时手动保护或模式不对），18:13 真离开时没有第二次事件，整晚停在上班。
- 现在：`ModeEngine.settle` 在每次地点事件和每次打开 App 时再判一次：现在是上班、人不在公司、今天 17:30 以后离开过公司或到了家、而且那之后模式没变过，就切到下班（来源是地点）。
- 手动保护只保护“地点变了之后”你自己选的模式；地点变化在手动切换之后，地点优先。
- 调试记录里“不切”后面写原因（现在的模式、2 小时内手动切过的时间）。
- 没做：后台定时唤醒（17:30 那一刻 App 不在前台、又没有地点事件时，要等下次打开或到家才切）；公司围栏半径还是设置里存的值。

### 数据存在哪（2026-10-07 核对，回应 Infra 初稿）

- 核对结果：属实。main 上所有记录只存在这台 iPhone 的 App Group 里：模式记录 `mode-log.json`、电量 `energy-log.json`、罐子账本 `can-ledger.json`（各角色的罐子、纪念品都在里面）、花销 `expense-log.json`；穿戴、开箱记录、设置在 App Group 的 UserDefaults。路径见 `HubContainer.swift`。
- 没有 iCloud 同步：代码里没有 CloudKit，也没有 NSUbiquitousKeyValueStore（唯一碰 iCloud 的是只读 Daily Widget 文件夹）。SwiftData + CloudKit 还是 M1b 的计划。Mac 版看不到手机的数据。
- 换手机或手机丢了：没有任何文件被排除出备份，所以按苹果的规则这些文件会进 iPhone 的 iCloud 备份或电脑备份，从备份恢复到新手机能带回来（推断，没在真机上验证过）。没开备份就全丢。
- 冻结期不改。要改就是 M1b：罐子账本和模式记录先上 CloudKit 私有库。
