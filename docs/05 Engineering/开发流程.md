# 开发流程

> 敏捷迭代，但 Git、环境和版本按大厂的常规做法来。一个人的项目，只保留真正有用的部分。先把 MVP 做完。

## 分支

主线开发（trunk-based）+ 版本 tag，大厂里最常见的一种：

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 主线，随时能编译、能发 STG | 只能通过 PR 合入，CI 必须绿 |
| `feature/<issue号>-<简短名>` | 新功能，例如 `feature/12-mode-widget` | 从 `main` 拉，合回 `main` |
| `fix/<issue号>-<简短名>` | 修 bug | 同上 |
| `chore/…`、`docs/…` | 工程杂项、文档 | 同上 |
| `hotfix/<版本号>` | PROD 出问题、但 `main` 上已有没发布的改动时 | 从对应的 tag 拉，修完打新 tag，再合回 `main` |

不设长期的 `develop` / `release` 分支：一个人开发，它们只会制造合并工作。需要冻结版本时直接打 tag。

## PR

- 每个改动都走 PR，一个 PR 只做一件事。
- 标题用 Conventional Commits：`feat: …`、`fix: …`、`chore: …`、`docs: …`、`refactor: …`、`test: …`。
- 合并方式：Squash merge，PR 标题就是 `main` 上的那条提交记录。
- 合并前：CI 绿（检查项见 [[CI-CD]]）；PR 描述按模板写 Before / After / How，并写清楚验证到了哪一级（能编译 / 真机验证过 / STG 装上用过）。
- 合并后删除分支。

## 环境

| 环境 | Xcode 配置 | Bundle ID | 名称 | 怎么装 | 数据 |
| --- | --- | --- | --- | --- | --- |
| **DEV** | Debug | `com.guanshiyang.lifehub.dev` | Life Hub DEV | Xcode 直接运行到模拟器或真机 | 测试数据，随便清 |
| **STG** | Staging | `com.guanshiyang.lifehub.stg` | Life Hub STG | `main` 上的版本 → TestFlight 内部测试 | 独立的测试数据 |
| **PROD** | Release | `com.guanshiyang.lifehub` | Life Hub | 打 tag 的版本 → TestFlight，Mike 每天用的就是它；以后想上 App Store 再走审核 | Mike 的真实数据 |

- 三个环境的 Bundle ID 不同，所以能同时装在一台手机上，数据互不影响。接入 iCloud 后，CloudKit 容器也按环境分开：`iCloud.com.guanshiyang.lifehub.stg` 和 `iCloud.com.guanshiyang.lifehub`。
- DEV 和 STG 的首页右上角有 `DEV` / `STG` 标签，PROD 没有。
- 签名用的 Team ID 在 Mike 本机的 Xcode 里选，不提交到仓库。

## 版本号

- **语义化版本** `MAJOR.MINOR.PATCH`，写在 `project.yml` 的 `MARKETING_VERSION`。
    - MVP 之前都是 `0.x`：每完成一个里程碑升 MINOR（M0 = 0.1.0，M1 = 0.2.0），修 bug 升 PATCH。
    - MVP 完成、Mike 连续用满两周 = `1.0.0`。
- **Build 号** `CURRENT_PROJECT_VERSION`：每次上传 TestFlight 加 1，只增不减。
- **发 PROD**：在 `main` 上打 tag `vX.Y.Z`，用 Release 配置 Archive，上传 TestFlight。
- 每个版本在 `CHANGELOG.md` 记一段（新增 / 修复 / 变更）。

## 功能拆分

- PRD 里每个功能开一个 GitHub Issue，打 `feature` 标签，挂到里程碑（M1 = PRD P0，M2 = P1）。
- 一个 Issue 对应一个 `feature/` 分支和一个 PR。
- 每个切片自己用满一周再做下一个（见 [[范围文档]]）。
