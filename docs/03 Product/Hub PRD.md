# Hub 功能设计（PRD 初稿）

> 依据：[[Life Hub 方向]]、两个副业笔记、已锁定的 companion（RUNNER v5，见 `companion/`）、Mike 工作中的 Attention Hub（截图 + 技术文档，见第 11 节）。技术框架线程「Hub 技术框架（工程）」读这份文档对齐，本文会原地更新。
> 优先级标记：**P0 = 第一版**，P1 = 第一版跑顺之后，P2 = 以后再说。

## 0. 第一原则：不是自律 App

Mike 2026-10-02 的总结：Lilo 和 Daily Widget 都是新鲜期一过就没再用，主要因为太依赖他主动打开、主动记录。所以这个 hub **不做成自律类型**。

- **什么都不做也要有价值。** 每个核心功能都要过这道题：如果 Mike 今天一下都没碰，它还给不给价值？过不了的功能只能是可选项，不能是核心。
- **记录、仪式、打卡全部可选。** 不提醒记录，不显示漏了几天，不做连续天数。
- **记状态和好回忆，不记账本。** 存的是“今天是什么状态、发生了什么好事”，不是任务清单和完成率。
- **入口是小组件和锁屏，不是打开 App。** App 在后台算好，小组件读结果。
- **一次只验证一个闭环。** 每一块先自己用一周，判断标准是“明天还想不想打开”，再加下一块。
- **界面上出现的功能都必须真的能用。** 没做完的不放上去。不做社交。

## 1. 一句话

一个只给 Mike 自己用的生活 hub：**一个产品，两个端**。companion（RUNNER）的模式就是 Mike 此刻的状态。iOS 是随身的“情绪价值 + 切换器”，Mac 是总控台 + 副业工具箱。

## 2. 产品结构

```
            ┌──────────── 共享核心（Core）────────────┐
            │ 模式状态机 · companion 状态 · 事件日志 · 同步 │
            └──────────────┬───────────────┬──────────┘
                     iOS 端                Mac 端
          切换模式 / 感知状态 / 陪伴     总控台 / 副业模式工具
```

- **共享核心**：当前模式、模式切换历史、companion 的情绪参数（energy）、每日记录。两端任一处切换，另一端几秒内跟上。
- **iOS 端**：随身。重点是“不用操作也知道我在什么状态”，以及切换模式那一下的仪式感。
- **Mac 端**：坐下来干活时用。看全局（今天/本周在各模式各花了多久），以及副业模式下的工具。

## 3. 核心概念：模式（Mode）

| 模式 | 典型触发 | companion 表现（已锁定） | 这一模式下 hub 做什么 |
| --- | --- | --- | --- |
| 上班 Work | 工作日上班时段 / 到公司 | 死人眼 + 耳机，面罩青色 LED | 安静陪着；下班倒计时；不打扰 |
| 下班 Chill | 下班后、周末 | 面罩拉到脖子，喝 Monster | 子活动：买菜 / 看剧 / 健身；轻松的小清单 |
| 拳击日 Boxing | 拳击训练日 / 到拳馆 | 赛博猫眼、虎牙、红头带，面罩拉下 | 训练前打气、训练计时、训练后记录 |
| 副业 Money | 手动进入，或周末拍摄日 | 面罩显示 ¥¥ | Mac 打开副业工具；iOS 显示今天的副业待办 |

规则：
- **同一时刻只有一个模式。** 切换是一等公民，每次切换写进日志。
- **默认自动，手动只是纠正。** 地点（到公司、到拳馆）+ 时间表（工作日上班时段、拳击日）自动切，不先问（Mike 2026-10-02 决定）。Mike 手动切换只用来纠正，纠正后同一地点短时间内不再自动覆盖，纠正记录用来改进规则。日历、Focus 先只做建议。
- Chill 的子活动（买菜/看剧/健身）做成 Chill 内的标签，不单独成模式（已确认）。
- 模式之内还有一个情绪维度 **energy**（沿用之前的 Energy × Load 思路，先简化成一条轴），驱动 companion 的细微表情；Rive 状态机输入已设计为 `mode / energy / tap / cheer`。

## 4. 情绪价值设计原则

1. **默认沉默。** 沿用之前结论：L0 只变表情，L1 打开 App 时说一句，L2 主动通知每天最多 1 条。
2. **切换要有仪式感。** 每次切换播一段 1–2 秒的过渡动画（例如下班：摘耳机、面罩拉下、开罐 Monster）。这是情绪价值最集中的地方。
3. **不制造愧疚。** 不做断签惩罚、不堆未完成项。没做到的事 companion 只会耸肩，不说教。
4. **夸要具体。** 拳击后、副业发帖后、拍完样片后给具体的 cheer（`cheer` 输入），而不是泛泛的“你真棒”。

## 7. 第一版（P0）范围

**要验证的唯一闭环：Mike 什么都不做，看一眼锁屏，RUNNER 就已经在对的模式、对的心情。**

做：
- iOS：自动模式（地点 + 时间表）、睡眠 → energy、小组件、首页 companion + 过渡动画、手动纠正、模式日志、可选的电量自评
- Mac：菜单栏 companion、总览面板、每个模式的传送门、副业模式的内容日历 + 手动参考库
- 两端同步

明确不做（第一版）：需要主动记录才有价值的功能、主动通知、爬取、自动发布、数据分析、短片生成、Watch、账号系统、自建后端、社交、给别人用。

交付顺序（每一块自己用一周再做下一块）：
1. **iOS 被动闭环**：自动模式 + 睡眠 energy + 小组件 + companion。
2. **定数据契约，再接 Mac**：先把共享数据格式定下来，再做 Mac 菜单栏和同步，同步要在两台真机上测。
3. **Mac 副业工具**：内容日历 + 参考库 + 传送门。

怎么算这一块成功（开工前定好，不用打卡类指标）：
- 自动模式切对：一周里 Mike 需要手动纠正的次数越来越少（起始目标：每天不超过 1 次）
- 一周里 Mike **没有被提醒**也自己看了 / 打开了至少 4 天
- Mike 自己的判断：“明天还想打开吗”，一周后仍然是“想”

停止或缩范围的条件（同样开工前写好）：
- 一周后自动模式还是经常切错 → 先修规则，不加新功能
- 两周里 Mike 只在新鲜期打开 → 停下来，回到第 0 节重想核心闭环，而不是加页面

证据分三级，汇报时分开说：源码里有、在本机验证过、已经装到 Mike 的手机/Mac 上。

## 10. 待和工程对齐

- 共享核心的数据模型：Mode、ModeSwitch（时间、来源：自动/手动纠正/建议）、Energy（来源：睡眠/自评）、可选的 DailyCheckin、GoodMoment（好回忆）、副业的 ContentItem / Reference / Booking
- 来自 Daily Widget 的经验（推断，待工程核实）：App 计算、小组件读快照；Mac 原生小组件需要原生 SwiftUI，不用 Electron；不自建后端和账号；先定数据契约再写第二个端
- companion 用 Rive，状态机输入 `mode / energy / tap / cheer`，两端同一个 `.riv`
- 小组件和菜单栏要能读当前模式（App Group / 共享存储）
- 副业的采集和发布要不要放在 Mac 端本地跑（浏览器自动化），取决于 Q5、Q6


## 11. 从工作 hub（Attention Hub）借来的东西

> 第 0 节优先：下面的仪式都改成自动生成或可选，不需要 Mike 主动做。

搬过来的：
- **Attention Bank 面板** → 电量一键自评（低电量/还行/满格）和 companion 的 energy；它的事件流水（专注、切换、打断、休息）对应这里的模式切换日志。
- **Rituals** → 早晨、下班 Wrap、每周回顾、随手记。工作 hub 的 Morning 全程不调用模型，这里的早晨也一样，用规则生成。
- **三栏布局 + 顶部问候语和当前模式** → Mac 总览面板。
- **Portals** → 每个模式一组传送门。
- **Inbox + 分拣** → P1 的收件箱（随手记、副业咨询、待决定）。
- **步骤进度条** → 副业每条内容、每单拍摄的进度显示。
- **几条原则**：能不用模型就不用；对外的动作（发帖、回私信）由 Mike 本人点；错误要显示出来；每份数据只有一个地方写。

不搬的：
- Jira 看板、PR 审查、herdr、PROD 发布流程：这些是工作专用，Work 模式下直接跳到工作 hub。
- SHIELD（过滤消息计数）：iOS 读不到别的 App 的通知，做不了；如果以后有能读到的来源再说。
- 模型分级（T0–T3）、Obsidian 作唯一数据源等实现做法交给工程线程判断。
